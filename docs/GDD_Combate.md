## 0. Por qué encaja donde ya está, sin inventar infraestructura nueva

Todo lo necesario para "coste cero" ya existe, solo hay que conectarlo — no hace falta una Room nueva, ni un tick, ni una rejilla de colisión distinta a la del mapa:

- **`Enemigo` en `HubState.ts`** lleva desde su creación el comentario "Sin movimiento/combate todavía (el streamer lo explicará aparte): un enemigo aparece quieto en su punto" — es el hueco exacto que este documento rellena.
- **`items.json` ya tiene los stats de combate sin consumidor**: `ataqueFisico`, `ataqueMagico`, `alcance`, `cooldownMs`, `defensaFisica`, `defensaMagica` (confirmado por grep — ver nota de catálogo, ninguna función los lee todavía), más `durabilidadMax`/`desgastePorUso` y toda `server/src/inventario/desgaste.ts` ya escritos y probados (21 tests puros) pero **sin ninguna Room que los llame** — el combate es su primer consumidor real.
- **La rejilla de la arena NO es nueva**: `server/src/mundo/colisiones.ts` (`MundoColision.casillas`, `tipoEn()`) ya clasifica cada casilla como sólida o no, y tanto `InteriorRoom` como `DungeonRoom` guardan `this.mundo`/`this.interior` con esa rejilla cargada. La arena de combate es un recorte NxN de esa MISMA rejilla centrado en el encuentro — cero autoría nueva, el mapa ya bakeado es la arena.
- **`DungeonRoom.poblarEnemigos`** ya puebla `state.enemigos` con `Enemigo` reales (x, y, enemigoId, esBoss) al entrar en una mazmorra — el combate se dispara sobre esas entidades que ya existen, no hace falta un spawner nuevo.
- **El patrón de mensajes `xxx:accion`** (`crafteo:iniciar`/`crafteo:recolectar`, `refinamiento:depositar`, `motriz:accionar`) ya es el idioma del proyecto para "el cliente pide, el servidor valida y aplica" — el protocolo de combate es más de lo mismo, no un mecanismo nuevo.
- **La UI ya es HTML/DOM plano inyectado sobre el canvas** (`client/src/construccion/constructor.ts`: `document.createElement`, `<style>` inyectado, paneles con `display:block/none`) y el propio `WorldScene` ya monta un `CSS2DRenderer` superpuesto a la cámara 3D para etiquetas — la UI de combate (retratos, barra de turnos, hotbar) sigue exactamente ese mismo patrón, no hace falta React ni un framework nuevo (el cliente no usa ninguno).

## 1. Disparo del combate — sin Room nueva, sin conexión nueva

Un combate vive DENTRO de la room donde ya está el jugador (`InteriorRoom`/`DungeonRoom` para PvE de mazmorra y fauna peligrosa en interiores; `RegionRoom` para fauna peligrosa en exterior — mismo mecanismo en ambas, ambas heredan `RoomExteriorBase`). No hay transición de room ni reconexión: el "modo combate" es un sub-estado replicado que se activa y desactiva sobre la MISMA conexión, así que no cuesta nada nuevo en el patch channel.

**Disparo**:
- **Jugador ataca a un `Enemigo`/fauna peligrosa** dentro de `RADIO_INTERACCION` (ya existe, usado por `coger`/`portal:usar`) → `combate:iniciar {objetivoId}`.
- **Fauna con `disposicion:"hostil"` o `"neutral"` provocada** (radio de agro, dato ya en `baker/catalogo/animales.json` desde el "Costura 2026-08-29" del Backlog, sin consumidor todavía) inicia combate ella misma cuando el jugador entra en su `radioAgro` — se resuelve de forma perezosa, en el mismo tick de movimiento que ya recalcula colisiones, no un tick nuevo.
- Varios jugadores pueden unirse al MISMO combate si atacan al mismo objetivo dentro de un margen corto (co-op contra un boss) — el combate no es 1v1 forzoso.

Al iniciarse: el servidor recorta un área NxN (8x8 encuentro normal, 10x10 contra boss — el tamaño lo decide `esBoss` del `Enemigo`) centrada en el punto de contacto, usando `tipoEn()` sobre `this.mundo` para marcar cada casilla walkable/obstáculo — si el recorte choca con el borde del mapa/interior se desplaza para caber entero, nunca se genera geometría nueva.

## 2. Estado replicado — nuevas Schema, mismo patrón que `HubState.ts`

```ts
// server/src/rooms/schema/CombateState.ts (código real, actualizado tras §9.1/§9.3)
export class CombateUnidad extends Schema {
  @type("string") id = "";           // sessionId del jugador o clave del Enemigo/Fauna/Npc (misma clave que state.enemigos/fauna/npcs/players)
  @type("boolean") esJugador = false;
  @type("string") bando = "A";       // "A" | "B"
  @type("int8") gx = 0;              // coordenada DENTRO de la arena (0..ancho-1), no del mundo
  @type("int8") gy = 0;
  @type("number") hp = 0;
  @type("number") hpMax = 0;
  @type("int8") pa = 0;              // recurso ÚNICO de turno (§9.3) — mover/atacar/objeto/magia salen del mismo pool
  @type("int8") paMax = 0;
  @type("number") iniciativa = 0;    // fija el orden, calculada una vez al empezar
  @type("string") estado = "activo"; // "activo" | "caido" | "huido"
  // Campos SOLO servidor (sin @type, snapshot tomado al entrar en combate):
  ataqueFisico = 0;
  defensaFisica = 0;
  alcance = 1;
}

export class CombateSchema extends Schema {
  @type("number") gx0 = 0;           // origen de la arena en coordenadas de mundo (para pintar el overlay)
  @type("number") gy0 = 0;
  @type("int8") ancho = 8;
  @type("int8") alto = 8;
  @type(["int8"]) obstaculos = new ArraySchema<number>(); // 1 = obstáculo, índice gy*ancho+gx
  @type(["string"]) ordenTurnos = new ArraySchema<string>(); // ids de CombateUnidad, por iniciativa desc
  @type("int8") turnoActual = 0;     // índice sobre ordenTurnos
  @type({ map: CombateUnidad }) unidades = new MapSchema<CombateUnidad>();
  // Ventana de unión (§9.1): "pendiente" = todavía se puede sumar gente
  // (ordenTurnos vacío, nadie juega turno), "activo" = ventana cerrada,
  // combate jugable de verdad. cierraEn: epoch ms, 0 si ya no aplica.
  @type("string") fase = "activo";
  @type("number") cierraEn = 0;
}
```

En `HubState.ts`: `@type({ map: CombateSchema }) combates = new MapSchema<CombateSchema>();` — un Map, no un único combate, porque una `DungeonRoom` puede tener varios grupos peleando en salas distintas a la vez sin bloquearse entre sí (mismo criterio que `construcciones`/`plantillas` ya son Maps por id, no un singleton).

## 3. Lógica de turnos — event-driven, CERO tick nuevo

Nada de `clock.setInterval` por combate activo (violaría la regla del proyecto). Todo se resuelve dentro del handler del mensaje que lo dispara, exactamente como `manejarCrafteoIniciar`/`manejarProduccionRecolectar` ya resuelven su lógica al vuelo:

- `combate:iniciar {objetivoId}` → crea `CombateSchema`, calcula iniciativa de cada unidad (stat base + variación pequeña por semilla del combate, determinista para que sea reproducible en test), puebla `ordenTurnos`, pone AP/MP al máximo de la primera unidad.
- `combate:mover {combateId, gx, gy}` → valida turno del que envía el mensaje, valida que `gx,gy` es alcanzable con el MP restante (BFS simple sobre la rejilla NxN — 64/100 casillas, trivial, `server/src/combate/pathfindingArena.ts`, reusa el mismo criterio de sólido que `tipoEn()`), descuenta MP gastado, actualiza `gx,gy`.
- `combate:accion {combateId, habilidadId, objetivoId}` → valida AP suficiente, alcance (distancia Chebyshev ≤ `alcance` del arma equipada, leído de `items.json` vía `inventario.ts`), línea de visión (Bresenham sobre `obstaculos`), resuelve daño = `ataqueFisico/ataqueMagico` del atacante − `defensaFisica/defensaMagica` del objetivo (server-autoritativo, el cliente solo sugiere — mismo criterio que todo el proyecto), aplica `desgaste.ts` (`registrarUso` al arma, `aplicarDanoArmadura` a la armadura del objetivo — primer enganche real de ese módulo), descuenta AP.
- `combate:pasarTurno {combateId}` → avanza `turnoActual`, si da la vuelta completa recalcula regen de AP/MP de cada unidad viva.
- Turno de un `Enemigo` (no hay cliente que envíe el mensaje): se resuelve automáticamente, en el mismo instante en que le toca en `ordenTurnos` — un cálculo síncrono y barato (IA simple: acercarse al jugador más cercano dentro de su MP, atacar si está en alcance) hecho DENTRO de `combate:pasarTurno`/`combate:accion` del jugador anterior, nunca en un timer propio.
- Combate termina cuando un bando entero queda `"caido"`/`"huido"`: se aplica el resultado (loot, XP si se define más adelante) y borra el `CombateSchema` del Map — vuelve a movimiento libre normal, sin más estado que limpiar. Si el bando caído era el de un `Enemigo` de una `DungeonRoom` y era el último con vida (`state.enemigos` se queda vacío), `DungeonRoom.finalizarMuerte` llama a `marcarMazmorraLimpiada(clave)` (§9.2 más abajo detalla cómo llega esa muerte hasta ahí desde la arena).
- **Corrección 2026-09-01 (cerrada)**: este párrafo afirmaba que el trigger de arriba "llama a `marcarMazmorraLimpiada`" cuando en realidad, comprobado con grep, **nunca se había implementado** — cero call sites, `DungeonRoom` no sobreescribía `finalizarMuerte`. Se detectó auditando el GDD, se dejó documentado como pendiente real, y en esta misma pasada se conectó de verdad: `DungeonRoom.finalizarMuerte` (que ya existía para el loot de jefes, ver `server/src/rooms/DungeonRoom.ts`) ahora también llama a un `comprobarMazmorraLimpiada()` privado tras cada muerte de `Enemigo` — si `state.enemigos` queda vacío, dispara `marcarMazmorraLimpiada`. Verificado con un E2E de combate real contra servidor Colyseus (`client/test/mazmorraLimpiada.e2e.cjs`, sin navegador, mismo patrón que `combate.e2e.mjs`): bakea una mazmorra de 2 enemigos, los mata uno a uno con combate táctico real (`godMode` para no depender de equipo/nivel), y comprueba que la instancia se repuebla vacía tras la limpieza — el lazo completo `muerte → marcarMazmorraLimpiada → obtenerLimpiezaMazmorra en la siguiente entrada` funciona de punta a punta.
  - Construir ese E2E destapó dos huecos reales del camino "combate resuelto en una arena aparte, resultado aplicado sobre la room de origen" (§9.2): (1) una `InteriorRoom`/`DungeonRoom` usaba el `autoDispose` por defecto de Colyseus — un jugador que salía SOLO a pelear a la arena dejaba su room de origen vacía, que se autodestruía antes de que el combate terminara, así que el resultado (esta limpieza, loot, XP) nunca llegaba a aplicarse sobre nada; afectaba a cualquier combate en solitario contra el último ocupante de un interior, no solo a este trigger. **Arreglado en una pasada aparte, misma fecha** (ticket de seguimiento sugerido y luego enviado por el streamer) — ver §9.2 más abajo. (2) `Player.godMode` es un campo por-room (`HubState.ts`) que NO viaja con el jugador de la room de origen a la arena (`ArenaCombateRoom.onJoin` crea un `Player` nuevo) — un test que active `godMode` solo en la room de origen puede ver morir a su propio jugador de verdad en la arena; no es un bug de producción (nadie usa `godMode` como mecánica real), solo una trampa a tener en cuenta al escribir E2Es de combate contra la arena.
- Único timer aceptable, y acotado: un `clock.setTimeout` POR combate activo para forzar `pasarTurno` si el jugador no actúa en ~30s (AFK) — se crea al entrar en el turno de ese jugador y se cancela al recibir su mensaje; no es un tick global, es el mismo patrón puntual y acotado que ya se aceptó para la economía de bandidos (10 min) — nunca un intervalo por room/jugador corriendo indefinidamente.

## 4. Protocolo Colyseus — mismo idioma que crafteo/motriz

| Mensaje | Payload | Valida | Efecto |
|---|---|---|---|
| `combate:iniciar` | `{objetivoId}` | objetivo en `RADIO_INTERACCION`, no en combate ya | crea `CombateSchema`, puebla arena y orden de turnos |
| `combate:mover` | `{combateId, gx, gy}` | es su turno, casilla alcanzable con MP restante, no ocupada | actualiza `gx,gy`, descuenta MP |
| `combate:accion` | `{combateId, habilidadId, objetivoId}` | es su turno, AP suficiente, alcance+LoS | resuelve daño/efecto, descuenta AP, aplica desgaste |
| `combate:pasarTurno` | `{combateId}` | es su turno | avanza `turnoActual`, resuelve turnos de enemigo en cascada |
| `combate:huir` | `{combateId}` | es su turno, casilla de borde de arena alcanzable | marca `"huido"`, sale del combate sin loot |

Todos cuelgan de `RoomExteriorBase` junto a los handlers de crafteo/motriz que ya están ahí (línea ~194-196) — no hace falta una clase de Room nueva ni un router aparte.

## 5. Cliente — misma cámara isométrica, overlay nuevo encima

**Grid overlay**: un `THREE.Group` de planos finos semitransparentes, uno por casilla de la arena, usando la MISMA conversión `posicionMundo(x,y)` que ya usa `WorldScene.añadirEntidad` (1 casilla = 1 unidad de mundo, sin sistema de coordenadas nuevo) — color por estado: verde = alcanzable con el MP restante (llega al recalcular tras cada `combate:mover`/cambio de turno), rojo = alcance de habilidad seleccionada, amarillo = AoE de la habilidad al pasar el ratón, gris = obstáculo. Vive en `client/src/combate/overlayArena.ts`, añadido/quitado de la escena vía `worldScene.añadirEstatico/quitarEstatico` (ya existen, pensados exactamente para geometría que entra y sale).

**Diferenciación de unidades**: círculo de selección bajo cada unidad (anillo `THREE.RingGeometry` plano en el suelo, azul=aliado, rojo=enemigo, amarillo=turno activo — se recolorea con `ordenTurnos[turnoActual]`) + barra de HP, ambos como `CSS2DObject` reusando el mecanismo que `WorldScene` ya tiene para las etiquetas de nombre (`añadirEntidad`/`textoEtiqueta`) — se extiende ese mismo div con una barra en vez de crear un renderer nuevo.

**Cámara**: sin cambios de proyección — `WorldScene.seguirPunto()` ya existe y ya suaviza el movimiento; al entrar en combate simplemente apunta al centro de la arena (`gx0+ancho/2, gy0+alto/2`) en vez de seguir al jugador, y vuelve a seguirlo al terminar. Cero código de cámara nuevo.

**UI de combate** (`client/src/combate/uiCombate.ts`), DOM plano igual que `constructor.ts`:
- Panel inferior-izquierdo: retrato + HP/Maná/Aguante/stats del héroe (lee `Player` + el ítem equipado vía `equipo` MapSchema).
- Panel inferior-derecho: mismo layout para el objetivo bajo el cursor/seleccionado.
- Barra inferior-central: iconos de habilidad con coste en AP superpuesto (deshabilitado en gris si no llega el AP restante), botón guardia, cambio de arma, consumibles, "pasar turno" — cada icono dispara `combate:accion`/`combate:pasarTurno`.

Todo el panel se muestra/oculta con `combate.activo` (colyseus `onChange`), mismo patrón que el panel de construcción ya hace con `_activo`.

## 6. Qué queda fuera de esta propuesta (a decidir después, con este contrato ya construido)

- El árbol de habilidades por arma/clase — aquí solo se fija que una "habilidad" cuesta AP, tiene alcance y puede tener AoE; el catálogo real de habilidades (ids, efectos, iconos) es trabajo posterior, como las recetas de Crafteo se rellenan oficio a oficio.
- PvP — el documento asume PvE (jugador contra `Enemigo`/fauna); si se activa combate entre jugadores es el mismo mecanismo (dos `CombateUnidad` con `esJugador:true`), pero el streamer ya apuntó que probablemente esté limitado/desactivado por defecto — se decide aparte.
- Recompensas (loot/XP) al ganar — se conecta con `jugador_oficios`/inventario cuando toque, no bloquea el mecanismo de turnos en sí.
- IA de enemigo más allá de "acercarse y golpear" (huir con poca vida, usar habilidades especiales de boss) — v1 cubre lo mínimo jugable, se afina con datos reales de playtesting.

## 7. Autosimulación cuando NO hay ningún jugador implicado (✅ confirmado 2026-08-30)

Pedido explícito: "en combates de NPC contra animales o NPC vs NPC se autosimule el combate" — sin turnos interactivos, sin UI, sin arena replicada a ningún cliente (nadie la está mirando). Mismo motor de reglas que el combate interactivo (§2-3: iniciativa, AP/MP, alcance, `calcularDanio`), pero resuelto SÍNCRONO y de una sentada, dentro del mismo handler/evento que detecta el encuentro — nunca un tick propio, mismo criterio "cálculo perezoso" de todo el proyecto.

- **Cuándo aplica**: cualquier combate donde `esJugador` es `false` en TODAS las unidades de ambos bandos — NPC humanoide (guardia/bandido) vs fauna peligrosa, NPC vs NPC (guarnición de un asentamiento hostil defendiéndose), fauna vs fauna si algún día se decide (depredador cazando, hoy sigue fuera per GDD_Agentes_Moviles.md). En cuanto CUALQUIER unidad tiene `esJugador:true`, el combate es interactivo (§1-6), nunca autosimulado.
- **Motor compartido, sin Schema**: `simularCombateAutomatico(bandoA, bandoB, arena, rnd)` (`server/src/combate/arenaCombate.ts`) reutiliza literalmente las mismas funciones puras que usará el camino interactivo (`ordenarTurnos`, `resolverAtaque`, `enAlcance`, pathfinding de arena) — NO es un sistema de combate aparte, es el mismo motor sin la capa de red/turnos-esperando-input. La IA de cada unidad en modo automático es la misma "acercarse al enemigo vivo más cercano y atacar si está en alcance" que ya describe §3 para el turno de un `Enemigo`.
- **Resultado**: se itera turno a turno en memoria (tope duro de iteraciones, p.ej. 50, para no colgarse si ninguno alcanza al otro) hasta que un bando queda entero `"caido"`, y se devuelve el estado final de vida de cada unidad — quien llama (el futuro sistema que detecte el encuentro: agro de fauna salvaje, guarnición bandida atacada) decide qué hacer con el resultado (aplicar HP final, generar cadáveres vía `matarIndividuo`/`crearCadaver` ya existentes, etc.). Determinista si se inyecta `rnd` fijo — mismo criterio de testeo que el resto del proyecto (`crearPRNG`/mulberry32).
- **✅ Disparador real ya cableado (esta misma pasada)**: `HubRoom.comprobarEncuentrosAutomaticos()`, cada 5s — recorre `state.npcs` × fauna salvaje ACTIVA (solo la de sectores cerca de jugadores, nunca las miles inactivas), y si alguna especie tiene `peligroso:true` (campo nuevo en `catalogoCombateFauna.ts`, viaja tal cual desde `baker/catalogo/animales.json`) dentro de 4 casillas de un NPC, resuelve el encuentro con `simularCombateAutomatico` y aplica el resultado (vida final, o `state.npcs.delete`/`onFaunaMuerta` si alguno cae). Un encuentro por pasada — sencillo a propósito, no una simulación masiva. **Sigue sin disparador para NPC-vs-NPC** (guarnición bandida vs guarnición): no existe ninguna entidad NPC-bandido viva en red todavía (`tropas_asentamiento` sigue siendo solo filas en BD, ver GDD_Faccion_Bandidos.md §2.4) — cuando exista, se conecta al MISMO `simularCombateAutomatico`, cero motor nuevo que escribir.

## 7bis. Agro por distancia contra JUGADORES (pedido 2026-08-30: "la orca/tiburón/depredador en agua debe funcionar como el depredador de tierra con triggers por distancia")

A diferencia de §7 (autosimulación NPC-vs-fauna, resuelve la pelea entera de golpe), esto abre un combate **interactivo** real (ventana de unión + arena + turnos, §9) SIN que el jugador tenga que pulsar `combate:iniciar` — la fauna ataca por su cuenta. Hasta esta pasada, TODO combate (contra fauna de tierra o de agua) era estrictamente iniciado por el jugador; `radioAgro` ya existía por especie en `baker/catalogo/animales.json` desde el principio pero no lo leía ningún código — pura casualidad de diseño que quedó pendiente hasta que el pedido de combate acuático (§9.6) hizo notar el hueco.

- **`RoomExteriorBase.verificarAgroFauna()`** (protected, reusable por Hub/Region): cada 200ms (mismo intervalo que ya tickea el merodeo de fauna), recorre `state.fauna` — cualquier especie `peligroso` (vía `estadisticasFaunaDe`) con un jugador (que no esté ya en combate) dentro de su `radioAgro` (`catalogoCombateFauna.ts`, RELLENO `RADIO_AGRO_DEFECTO=5` si la especie no trae el campo) dispara `iniciarCombateFaunaVsJugador(faunaId, jugadorId)` — mismo montaje de arena/`CombateSchema`/ventana de unión que `manejarCombateIniciar`, sin `esModoCaza` (una especie `peligroso` nunca es presa pasiva) ni `retorno` capturado (el jugador vuelve al Hub por defecto al terminar — mismo fallback que ya usa `ArenaCombateRoom` para un PvP sin retorno). Un encuentro por pasada, mismo criterio de sencillez que `comprobarEncuentrosAutomaticos`.
- **Cubre agua Y tierra por igual, sin caso especial**: como `state.fauna` no distingue especies acuáticas de terrestres (ambas son la misma Schema), el mismo bucle ya cubre orca/tiburón (que además, si el jugador va en barco, disparan la arena de agua y el visual cosmético de §9.6) — el pedido de "que funcione como el depredador de tierra" se cumple literalmente por construcción, un único mecanismo para los dos.
- **Guarda contra doble-combate** (`enOtraArena: Set<string>`, nuevo): una fauna que ya se fue a pelear a una room de arena aparte SIGUE viva en `state.fauna` de esta room hasta que la pelea termine (nadie la borra) — sin esta guarda, `verificarAgroFauna` (cada 200ms) la habría metido en un SEGUNDO combate simultáneo contra otro jugador mientras la primera pelea seguía en curso en otro sitio. Se marca al cerrar la ventana de unión (`cerrarVentanaCombate`) y se limpia cuando el resultado remoto vuelve (`aplicarResultadoRemoto`) — el mismo guardado protege también a `manejarCombateIniciar` (un jugador ya no puede intentar `combate:iniciar` contra un bicho que está fuera peleando).
- **Verificado con un E2E real** (`server/test/agroFauna.e2e.mjs`): siembra una orca (BD `fauna_salvaje`) a 1.6 casillas del spawn de `test_mar_a` (mismo mapa de prueba 100% agua de §9.6/`docs/GDD_Barcos.md`), se une SIN mandar ningún mensaje de combate, y confirma que llega `portal:ir {tipo:"combate"}` sin que el jugador pidiera nada — la ventana de unión real dura 60s (`VENTANA_UNION_COMBATE_MS`), el test usa `combate:comenzarYa` (mismo atajo que un jugador con prisa) para no esperar el minuto entero.
- **Explícitamente fuera de esta pasada**: sin cooldown de re-agro tras huir/ganar (una vez el jugador sale del radio, `verificarAgroFauna` simplemente deja de encontrarlo — no hay memoria de "ya me atacó hace poco"); sin aviso visual previo al jugador (el pedido no lo mencionaba, mismo criterio "sin UI de targeting/confirmación" del resto del combate).
- **Extendido a `Npc` hostil** (docs/GDD_Faccion_Bandidos.md §7ter, pedido 2026-08-30, "patrulla de reclutas bandidos"): `verificarAgroFauna` ahora también recorre `state.npcs` y dispara el mismo `iniciarCombateFaunaVsJugador` para cualquier `Npc.hostil===true` — un civil normal de `poblacion/` nunca tiene ese flag, así que esto no les afecta en nada. `cerrarVentanaCombate` (§9.1, abajo) recibió el mismo tratamiento: el auto-unión de hostiles cercanos ahora también suma cualquier `Npc.hostil`, no solo `Enemigo`/`Fauna` peligrosa — así se une el grupo de patrulla entero si estaban "al lado".

## 9. Combate INSTANCIADO en arena aparte + PA único (pedido 2026-08-30, ✅ IMPLEMENTADO y verificado 2026-08-29)

Con el v1 de arriba (§0-8) ya construido, probado y jugable tal cual (misma room, AP+MP, UI placeholder), el streamer pidió la siguiente vuelta: que el combate se INSTANCIE en un mapa de arena aparte en vez de resolverse en el sitio, con una ventana de tiempo para que se sumen más combatientes antes de empezar. Es un cambio real de arquitectura sobre código YA verificado con E2E, así que se documentó primero (esta sección) y se implementó tras el OK explícito del streamer — mismo criterio que el resto de sistemas grandes del proyecto.

**Verificación realizada**: 354/354 tests de `server` en verde, `tsc --noEmit` limpio en `client` y `server`, `client/test/combate.e2e.mjs` (jugador vs fauna salvaje del mapa demo, HubRoom → ventana pendiente → `comenzarYa` → arena instanciada → combate jugado hasta la muerte → `portal:ir` de vuelta al Hub → la fauna REAL del Hub, no la sintética de la arena, desaparece tras rejoin) y un E2E manual adicional en PvP (dos jugadores en una `region`, ventana de unión con ambos ya apuntados, `comenzarYa`, misma room de arena para los dos, `ordenTurnos` remapeado a `sessionId` real, combate jugado hasta el final, retorno exacto para el iniciador y fallback a Hub para el objetivo sin retorno propio, marcador de "combate en curso" visible a un tercer cliente espectador y borrado al terminar) — ambos en verde.

### 9.1 Ventana de unión — combate PENDIENTE antes de instanciar nada

`combate:iniciar {objetivoId}` (mismo trigger de §1) deja de crear la arena al instante — crea un `CombateSchema` con una fase `"pendiente"` en la room ACTUAL (exterior/interior donde se cruzaron), visible a todos ahí, con `cierraEn = Date.now() + 60_000`:

- **Jugadores** dentro de `RADIO_INTERACCION` del punto de origen ven un prompt "Unirse al combate" → `combate:unirse {combateId}`.
- **NPCs/fauna** dentro de ese MISMO `RADIO_INTERACCION` (2.2 — `RoomExteriorBase.ts:44`, la única constante de "cerca" que ya usa todo el proyecto, no se inventa un radio nuevo) se unen AUTOMÁTICAMENTE sin turno del jugador: extensión directa del agro que ya existe (`HubRoom.ts` — un animal ataca si el objetivo está a `< RADIO_INTERACCION`).
- Cualquier participante ya apuntado puede pulsar "Comenzar ya" (`combate:comenzarYa {combateId}`) para saltarse lo que quede de los 60s.

**Excepción — modo caza** (docs/GDD_Caza.md, pedido 2026-08-30): si el objetivo es Fauna NO peligrosa (`!faunaEsPeligrosa`, ver §5.4 de GDD_Mecanicas), `manejarCombateIniciar` NO abre ventana — cierra al instante (`cerrarVentanaCombate` síncrono, sin `clock.setTimeout`) y sin auto-unión de nada, ni siquiera Enemigo de mazmorra cercano (`combatesSinAutoUnion`, estrictamente 1 vs 1). La presa entra como unidad `pasivo:true`: en su turno deambula sin rumbo (`jugarTurnoIAPasiva`, `arenaCombate.ts`) y nunca ataca ni persigue, esté el jugador a tiro o no. Fauna peligrosa (jabalí/lobo/oso...) sigue el camino normal de esta sección.

### 9.2 Al cerrar la ventana — teleport a una room de arena nueva, placeholder en el origen, vuelta al terminar

- El servidor elige una arena (§9.4) y crea una room de arena NUEVA, una por combate (`filterBy(["combateId"])`, mismo patrón de instancia por clave que ya usan `interior`/`mazmorra`, `server/src/index.ts:28-32`) — manda a cada participante el MISMO mensaje que ya existe para cambiar de room, `client.send("portal:ir", {tipo:"combate", combateId, x, y})` (el cliente ya reacciona a esto y reconecta, `client/src/game.ts`) — cero mecanismo de teleport nuevo, el portal de siempre apuntando a otro sitio.
- **Placeholder en el mapa de origen**: al abrirse la arena, la room de origen deja un marcador (`MarcadorCombateSchema`: x, y, participantes) en un `MapSchema` nuevo de `HubState` (`combatesEnCurso`) mientras dure la pelea — visible a cualquiera que pase por ahí. Se borra al terminar.
- **Vuelta**: la room de arena guarda por participante `{tipoOrigen, mapaId, x, y}` capturado al entrar — al acabar el combate manda el `portal:ir` inverso a esas coordenadas exactas. Mismo patrón que `InteriorRoom.ts` ya usa para "salir por la puerta".
- **Resultado de un NO-jugador (fauna/enemigo/npc) sobre su entidad real**: `ArenaCombateRoom.onCombateResuelto` resuelve la room de origen con `matchMaker.getLocalRoomById(origenRoomId)` (mismo proceso, "un solo servidor") y llama a `origen.aplicarResultadoRemoto(id, hp, estadoFinal, jugadoresGanadores)` por cada unidad no-jugador — aplica la vida final y, si `estadoFinal==="caido"`, `finalizarMuerte(id)` **sobre la instancia real de la room de origen** (no la copia sintética de la arena), así que cualquier override de `finalizarMuerte` de una subclase (`InteriorRoom`, `DungeonRoom` §3) se ejecuta con normalidad. Para que esto funcione, `matchMaker.getLocalRoomById` tiene que encontrar la room de origen TODAVÍA VIVA — ver el punto siguiente.
- **Corrección 2026-09-01 (bug real, no solo de test — ver el hueco (1) que documenta el párrafo de arriba)**: `RoomExteriorBase` usaba el `autoDispose` por defecto de Colyseus en TODA room — si un jugador se iba solo (`room.leave()`) a pelear a la arena, su room de origen se quedaba a 0 clientes y Colyseus la destruía antes de que `onCombateResuelto` pudiera resolverla con `matchMaker.getLocalRoomById`, perdiendo en silencio el resultado (loot, XP, cualquier hook de subclase). Arreglado con `autoDispose` dinámico, atado a la señal que ya existía para esto (`state.combatesEnCurso`, un `MapSchema` que ya se poblaba en `cerrarVentanaCombate` y se vaciaba en `quitarMarcadorCombate`, solo que nadie lo usaba todavía para decidir si disponer la room): `cerrarVentanaCombate` pone `this.autoDispose = false` junto con el marcador; `quitarMarcadorCombate` (la llama la arena al resolver, ver arriba) lo revierte a `true` si aún queda algún cliente conectado, o llama a `this.disconnect()` para disponer la room A MANO ahora mismo si ya no queda ni cliente ni combate pendiente (Colyseus no vuelve a comprobarlo solo porque `autoDispose` cambie, hay que pedírselo). Verificado con `client/test/combateSoloMantieneRoom.e2e.cjs`: un jugador SOLO mata al único enemigo de una mazmorra saliendo a la arena, y se comprueba (a) que la `DungeonRoom` de origen no se recreó durante la ventana en que el combate estaba resuelto en la arena pero el jugador aún no había vuelto a entrar, y (b) que el resultado se aplicó de verdad (no repuebla al reentrar) — confirmado además que el test SÍ detecta la regresión (revirtiendo el fix, la reentrada repuebla el enemigo "muerto"). Sin cambios de comportamiento para el resto de rooms sin combate pendiente: siguen disponiéndose exactamente igual que siempre en cuanto se vacían.
- Combate SIN jugadores (§7) sigue exactamente igual — la autosimulación NUNCA instancia nada.

### 9.3 Un único recurso de turno: PA (sustituye AP+MP del v1)

Colapsa `ap`/`apMax`/`mp`/`mpMax` de `CombateUnidad` en un solo `pa`/`paMax`, del que salen las cuatro acciones del turno:

- **Mover**: `pa` por casilla (Chebyshev, mismo cálculo de `casillasAlcanzables` en `pathfindingArena.ts`, solo cambia qué contador se resta).
- **Combate**: `pa` fijo por golpe (placeholder de balance).
- **Objetos**: mismo `personaje:consumir` (`docs/GDD_Personaje.md §4`), solo en el turno propio dentro de un combate activo, cuesta `pa`.
- **Magia**: sin catálogo de hechizos todavía (§8) — mismo hueco "habilidad con coste en `pa`" que una acción de combate normal.

**Ampliación 2026-08-31 (pedido streamer, evaluando un plan externo de "Gemini" con PA por Agilidad/EasyStar.js/boardgame.io — descartados los 3: el proyecto ya tenía este sistema, solo le faltaba el disparador de cliente):**

- **`combate:mover` ahora tiene disparador real**: hasta esta pasada el servidor lo validaba todo (turno, PA, alcanzabilidad) pero NINGÚN cliente lo llamaba nunca — protocolo puro sin consumidor. Ahora las MISMAS teclas WASD/flechas del mundo abierto (`game.ts`) mandan un paso discreto de `combate:mover` mientras `SALA==="arena"` **y** es tu turno — el movimiento libre continuo (`input`) se salta entero dentro de una arena, tanto en cliente (no se manda) como en servidor (`RoomExteriorBase`: cualquier `input` de un jugador con una `CombateUnidad` en fase `"activo"` se ignora, `x=y=0` forzado — nunca te fíes solo del cliente). Fuera de combate (Hub/Región/Interior/mazmorra normal) cero cambios, exactamente el movimiento libre de siempre.
- **BUG REAL corregido**: `combate:mover` solo tocaba `CombateUnidad.gx/gy` (la posición TÁCTICA), nunca `Player.x/y` (lo que de verdad interpola el rig en `game.ts`) — el servidor registraba el movimiento perfectamente pero el rig se quedaba clavado en el sitio. Ahora sincroniza también `Player.x/y` (o `CompaneroSchema.x/y` si la unidad movida es un compañero, vía `unidadId`).
- **Coste de terreno real** (`pathfindingArena.ts`): `Arena.costes` opcional (ausente = todo cuesta 1, compatible con la autosimulación §7 y cualquier arena sin datos), poblado por `ArenaCombateRoom` a partir del `modVelocidad`/`TIPO.AGUA` que `cargarMapaColision` ya calculaba (sin catálogo nuevo) — agua o `modVelocidad<1` cuesta 2 PA por casilla, el resto sigue costando 1. `casillasAlcanzables`/`costeCasilla` pasaron de BFS uniforme a un Dijkstra pequeño (tablero ≤900 casillas, sin cola de prioridad) que de verdad prefiere un rodeo más largo pero más barato en vez del camino recto si cruza terreno caro.
- **Huir con probabilidad real** (antes: éxito garantizado, sin tirada ni coste): exige ≥1 PA, consume TODO el PA restante pase lo que pase, y tira contra `probabilidadHuirPorCarisma` (`bonusAtributos.ts`, mismo patrón "por nivel 1-10" que el resto del fichero — no el "Carisma×2.5% en bruto" del plan externo, este proyecto no tiene esa escala): 30% en nivel 1, 52.5% en nivel 10. Fallo: `combate:error` (motivo "intento de huida fallido"), agota el turno igual, pasa al siguiente — éxito: mismo camino de salida de siempre.
- **PA visible en el panel** (`panelCombate.ts`): antes solo mostraba HP — sin ver el PA restante el jugador no podía decidir nada. Ahora "Tú: HP — PA: x/y" + aviso "WASD para moverte" en tu turno.
- **Descartado explícitamente reusar librerías externas** (evaluación pedida por el streamer): `boardgame.io` correría un segundo sistema de turnos/estado en paralelo a Colyseus, que ya es la autoridad; `EasyStar.js` es redundante con el Dijkstra propio de arriba, hecho a medida para esta rejilla Chebyshev de 8 direcciones; los 2 templates de Phaser no aplican ni como código de referencia (el proyecto migró a Three.js).
- Verificado con `server/test/{pathfindingArena,arenaCombate,bonusAtributos}.test.ts` (946/946 en verde) y 2 E2E visuales reales extendidos con un paso de movimiento (`client/test/combateArena{Tierra,Acuatico}.e2e.mjs`): confirman coste 1 PA en tierra / 2 PA en agua, y que el rig visual se mueve de verdad, no solo la unidad táctica.

### 9.4 Mapas de arena — bakeados por bioma/interior, uno elegido por combate

Arenas NxN pequeñas, mismo formato de sectores que el resto de bakeadores (compatible con `MundoColision`/`tipoEn()`, cero parser nuevo) — `assets/mapas/arenas/<bioma>/<variante>.json` (+ `interior/<variante>.json`). Catálogo nuevo (`mazmorras/catalogo/arenas.json` o similar) lista variantes por bioma; al cerrar la ventana de unión el servidor elige una determinista por semilla del combate (mismo `elegirPonderado`/PRNG mulberry32 de siempre) entre las del bioma/interior de origen. Bake tool nuevo y pequeño (reusa `mazmorras/src/celular.js` para el contorno — sin salas ni mobiliario, una arena es solo suelo+obstáculos). ### 10.1 `habilidadId` deja de ignorarse — golpe especial por FAMILIA de arma

El protocolo (§4) aceptaba `habilidadId` en `combate:accion` desde el principio pero lo ignoraba por completo (§8 lo documentaba como hueco conocido). Ahora cada una de las 31 armas de `items.json` (`tipo:"arma"`) lleva un campo de catálogo nuevo, `habilidadId: "familia:accion"` — agrupadas por `tipoDano`+alcance+identidad real del arma, **nunca herramientas** (`tipo:"herramienta"`, fuera de alcance a propósito, no tienen ni `ataqueFisico`):

| Familia | Armas | Mecánica |
|---|---|---|
| `daga:puntoDebil` | daga(+bonificada), cuchillo_piedra | Ignora 30% de la defensa del objetivo (golpe preciso, busca el hueco de la armadura) |
| `espada:estocada` | espada_corta/larga(+bonificadas), cimitarra(+bonificada) | +25% de ataque plano (estocada técnica, la familia "genérica") |
| `hacha:tajoPesado` | hacha_combate(+bonificada), hacha_piedra | +40% de ataque si el objetivo NO se movió en su turno más reciente (castiga al que no maniobra) |
| `maza:aturdir` | maza_guerra(+bonificada), garrote_madera, martillo_guerra(+bonificado) | 25% de aturdir al objetivo — pierde su próxima acción entera |
| `baston:barrido` | baston_guerra | Mismo daño base, reduce 1 el PA restante del objetivo (golpe de barrido, lo desestabiliza) |
| `lanza:embiste` | lanza(+bonificada), jabalina(+bonificada), tridente(+bonificado) | Empuja al objetivo 1 casilla en línea recta alejándose del atacante (si la casilla está libre) |
| `arco:apuntar` | honda, arco_corto/largo(+bonificados), ballesta(+bonificada) — TODA arma con munición, sea `tipoDano` perforante o contundente | "Quedarse quieto y disparar dos veces": exige no haberse movido este turno, cuesta el doble de PA y munición, dos impactos en cascada |

Motor puro nuevo en `server/src/combate/arenaCombate.ts`: `habilidadDeEquipo` (mismo patrón que `alcanceDeEquipo`/`municionDeEquipo`), `golpesDeHabilidad`/`costeExtraPaDeHabilidad`/`municionExtraDeHabilidad`/`requiereQuietoHabilidad` (predicados por familia, hoy solo `arco:*` devuelve algo distinto del valor base) y `resolverAtaqueConHabilidad` (el switch por familia — `golpear()` interno factoriza el cálculo de daño+absorbido que antes solo vivía en `resolverAtaque`, que ahora es un caso particular de `golpear` sin modificador).

**Sin árbol de habilidades, sin XP que desbloquee nada**: el jugador tiene la variante en cuanto tiene el arma equipada. `CombateUnidad.habilidadId` (server-only) es un SNAPSHOT tomado al crear la unidad (`crearUnidadCombate`, desde `habilidadArmaJugador(sessionId)` en la room de ORIGEN, mismo momento que ya snapshotea `alcance`/`municionId`) — `manejarCombateAccion` **nunca confía en lo que mande el cliente**: `msg.habilidadId` solo se acepta si coincide EXACTO con ese snapshot, cualquier otra cosa (vacío, inventado, la habilidad de un arma que no llevas) cae al ataque base de siempre. El ataque base ("golpear con lo que tengas", sin `habilidadId` o con uno no reconocido) sigue funcionando EXACTAMENTE igual que antes — verificado con `client/test/combate.e2e.mjs`/`combateCoop.e2e.mjs` en verde tras el cambio, sin tocar una línea de esos tests.

Dos campos nuevos server-only en `CombateUnidad`, threaded roster→arena igual que `municionId`/`alcance` (`ParticipanteArena.habilidadId`, `server/src/combate/registroArenas.ts`):

- **`movioEsteTurno`**: `true` si la unidad se movió en su turno más reciente (`combate:mover`, o `jugarTurnoIA` cuando la IA decide desplazarse) — reseteado a `false` para TODAS las unidades activas en cada vuelta completa (`RoomExteriorBase.avanzarTurno`, mismo punto que ya regeneraba PA). Lo leen `hacha:tajoPesado` (sobre el OBJETIVO) y `arco:apuntar` (sobre el propio ATACANTE, exige que valga `false`).
- **`aturdido`**: lo pone `maza:aturdir` con 25% de probabilidad. Mientras vale `true`, la unidad no puede atacar/mover/huir/usar un objeto (guardias nuevos en los 4 handlers correspondientes, mismo mensaje de error) — para un jugador, la única salida es `combate:pasarTurno` (`avanzarTurno` limpia la bandera de la unidad cuyo turno acaba de terminar, antes de avanzar el índice); para una IA, `jugarTurnoIA` la consume y no hace nada ese turno (ni se mueve ni ataca).

`arco:apuntar` se resuelve con un bucle genérico en `manejarCombateAccion` (`golpes = golpesDeHabilidad(...)`, 1 o 2) que llama a `resolverAtaqueConHabilidad` en cascada, acumulando daño/absorbido — el resto de familias usan `golpes=1` y el mismo camino, sin ningún `if` especial para "es arco".

## 10.5 `estaRoto`/`factorDurabilidad` consultados de verdad en combate + rotura probabilística + reparar (pedido streamer 2026-09-03: "un arma rota pierde el 80% de su daño se puede usar con ese debuff y reparar... que combate lo consulte")

Hasta esta fecha `calcularStatsEquipo` (`server/src/inventario/inventario.ts`) sumaba `ataqueFisico`/`defensaFisica` de cada pieza equipada EN BRUTO, ignorando su durabilidad real por completo — confirmado leyendo el código. Cerrado en 4 piezas, todas alrededor de lo mismo:

### 10.5.1 El desgaste GRADUAL ya afecta el ataque/defensa real (fuera y dentro de combate)

`desgaste.ts` gana dos piezas nuevas, reusadas por todo lo demás de esta sección:

- **`FACTOR_ITEM_ROTO = 0.2`**: un ítem ROTO (`estaRoto` true) NO deja de funcionar — rinde un SUELO FIJO del 20% de su ataque/defensa normal (80% menos, pedido literal), nunca el 0% que daría `factorDurabilidad` de forma lineal al llegar a 0. Deliberadamente un suelo fijo y no "lo mismo que factorDurabilidad en el extremo" — así "roto" es un estado jugable con debuff claro, no "inservible".
- **`factorRendimiento(instancia, entrada)`**: combina `estaRoto`/`factorDurabilidad` en una sola llamada — roto = `FACTOR_ITEM_ROTO` exacto, sano = `factorDurabilidad` normal (decae lineal con el desgaste).

`calcularStatsEquipo(catalogo, equipo, equipoDurabilidad?)` gana un tercer parámetro OPCIONAL (compatibilidad con los pocos call-sites/tests que no tenían a mano la durabilidad real) — con él, cada pieza con `durabilidadMax` aporta su ataque/defensa multiplicado por `factorRendimiento` de esa pieza concreta (`equipoDurabilidad[slot]`, ausente = a tope). Los 4 call-sites reales (`recalcularStatsJugador`, `spawnearCompanero`, `otorgarXpCompanero`, `sincronizarYRecalcularCompanero`, todos en `RoomExteriorBase.ts`) ya pasan la durabilidad real — así que `Player.ataque`/`Companero.ataque` (que alimentan `crearUnidadCombate` al entrar en combate) YA reflejan el desgaste real de lo equipado, sin ningún cambio adicional en el motor de combate: un arma medio gastada pega menos desde el primer golpe de la pelea, una rota pega al 20% desde el primer golpe.

### 10.5.2 Rotura PROBABILÍSTICA de golpe — mecanismo NUEVO, aparte del desgaste gradual

Pedido literal: "cada golpe conectado tiene una probabilidad (base 20%) de romperse, si tiene mas nivel del oficio herreria baja". Esto es un mecanismo DISTINTO de `registrarUso`/`golpesDados` (que ya desgastaba 1 punto de durabilidad por golpe, §10.2) — cada golpe del ATACANTE tiene además una tirada aparte de romper el arma DE GOLPE, sin importar cuánta durabilidad le quedara.

- **`probabilidadRoturaArmaPorNivelHerrero(nivel)`** (`server/src/personaje/oficios.ts`) — lineal entre nivel 1 (20%, `PROB_ROTURA_ARMA_NIVEL_1`) y nivel 10 (5%, `PROB_ROTURA_ARMA_NIVEL_10`), mismo estilo que `bonusVelocidadCrafteoPorNivelOficio` pero invertida (a más nivel, MENOS probabilidad). Usa `nivelDeXp(bd.obtenerXpOficio(jugadorId, "herrero"))` del ATACANTE — **no hace falta tener "herrero" elegido en `oficio1`/`oficio2`** (mismo criterio que los blueprints legendarios, `NIVEL_MINIMO_SASTRE_LEGENDARIO`: se lee la XP acumulada aunque no esté "activo" como oficio), 0 XP (nunca tocado) = nivel 1 = 20%, el suelo más alto.
- **Tirada real** en `manejarCombateAccion` (`RoomExteriorBase.ts`), tras resolver el golpe: solo si el atacante `esJugador`, su arma en `manoPrincipal` tiene `durabilidadMax` Y todavía no está rota (ni por desgaste gradual previo ni por otro golpe de ESTA pelea) — un arma ya rota no puede "romperse más". Si sale, marca `CombateUnidad.armaRotaEnCombate = true` (campo nuevo, server-only, mismo patrón exacto que `aturdido`/`movioEsteTurno`) y notifica al jugador (`combate:armaRota {itemId}`).
- **Efecto INMEDIATO dentro de la pelea**: `unidadDesdeSchema` (que construye la `UnidadCombate` pura que usa `resolverAtaqueConHabilidad`) aplica `FACTOR_ITEM_ROTO` sobre el snapshot `ataqueFisico` cuando `armaRotaEnCombate` es `true` — el resto de golpes de esa unidad, EN ESE COMBATE, rinden al 20%, sin tocar `CombateUnidad.ataqueFisico` en sí (el HUD/stats base no mienten a media pelea) ni el arma sigue rompiéndose más (`estaRoto` ya sería `true` de todas formas una vez la durabilidad real llegue a 0 al terminar el combate).

### 10.5.3 Reparar — mínimo viable NUEVO (no existía NADA que reparar)

Confirmado leyendo el código: hasta esta fecha no había ningún mensaje/mecánica de reparación en todo el repo (`grep -rn "reparar" server/src/` solo encontraba "prepararX" de crafteo/cocina/alquimia, sin relación). Construido el mínimo real y funcional:

- **`item:reparar {construccionId, slot?, instanciaId?}`** (`RoomExteriorBase.ts`) — repara UN objeto con durabilidad, EQUIPADO (`slot`) o SUELTO en el inventario/mochila (`instanciaId`, `slot` gana si llegan los dos). Deja la durabilidad al MÁXIMO de una sola tirada (decisión "mantenlo simple": sin reparación parcial en varias visitas — con el material a mano, un jugador siempre puede dejar un arma/pieza sana del todo en un solo golpe de martillo).
- **Gate**: junto a un yunque real (`OBJETOS_YUNQUE_REPARACION = {"yunque_tocon", "yunque_cuerno"}`, las dos mesas reales de herrero que ya craftean armas — `items/catalogo/recetas.json`) — MISMO gate para armas Y armadura: la inmensa mayoría de lo desgastable real del catálogo es metal (armas + cascos/brazos/manos/piernas de hierro/acero), así que un único gate es más simple que inventar 3 estaciones distintas para cubrir un puñado de piezas de cuero/madera cada una. Sin distancia explícita exigida (mismo criterio que `manejarCrafteoIniciar`, que tampoco la comprueba).
- **Insumo real**: `insumoReparacionDe(entrada, itemId)` — `familiaMaterial` del catálogo si lo declara (las armas SÍ lo declaran: metal→`lingote_hierro`, madera→`madera_dura`, cuero→`cuero_curtido`, tela→`tela_hilada`, piedra→`piedra_tallada`, precioso→`gema_tallada`, cantidad pequeña fija — mismo criterio "número de referencia" que `INSUMOS_COPIA_SASTRE`/`INSUMOS_COPIA_CARPINTERO`); la ARMADURA no declara `familiaMaterial` en `items.json` (solo las armas), así que se infiere por sufijo real del itemId (`acero`/`hierro`/`cuero`/`madera`) — ítem sin familia NI sufijo reconocido = "no se puede reparar", rechazo claro en vez de adivinar mal.
- **Sin oficio obligatorio**: self-service, cualquiera con el material y la estación puede reparar — decisión deliberada, el oficio herrero ya pesa de verdad en esta misma pasada (baja la probabilidad de ROTURA en combate, §10.5.2); exigir ADEMÁS nivel de herrero para reparar penalizaría dos veces al mismo jugador por lo mismo.
- Restaura `player.ataque`/`defensa` al instante (`recalcularStatsJugador`), responde `item:reparado {itemId, durabilidad}`; sin material suficiente responde `item:error {motivo}` (nunca revienta, nunca repara gratis).

## 11bis. Bug real encontrado corriendo `mazmorraLimpiada.e2e.cjs` de verdad: un jugador arrastrado a un combate por agro/co-op que nunca conecta a la arena bloqueaba el turno para siempre (2026-09-07, mismo día)

## 11quater. Causa raíz REAL del "Sin roster" intermitente (dos bugs de servidor, no uno) + dos límites del propio test (2026-09-07, investigación dedicada, instrumentando con logs temporales el matchmaking de Colyseus y el ciclo de vida de `combate:*`)

§11bis dejó la carrera "Sin roster"/"instancia sigue viendo 1 enemigo" sin cerrar, con la hipótesis (sin confirmar) de que el `retry(fn, 5, [SeatReservationError])` de `joinOrCreate` de colyseus.js pudiera estar creando `ArenaCombateRoom` DOS veces para el mismo `combateId`. Instrumentando `node_modules/@colyseus/core/build/MatchMaker.js` con logs temporales (nunca comiteados — está en `.gitignore`) se descartó esa hipótesis a la primera: el fallo salía en el intento **1 de 1**, sin ningún retry — `ArenaCombateRoom.onCreate` reventaba "Sin roster" la primera y única vez que se llamaba `joinOrCreate("arena", ...)`. La causa real estaba en el lado de la aplicación, no en Colyseus.

**Bug real nº1 — server, `manejarCombateIniciar` rechazaba al atacante si YA estaba en OTRO combate propio (comportamiento CORRECTO), pero el test asumía que su `objetivoId` preferido era siempre el enemigo real.** El test entra con los dos jugadores literalmente ENCIMA del spawn de un enemigo (a propósito, ver cabecera del fichero: evita resolver pathfinding real dentro de una cueva orgánica) — con el agro automático de §11 (`verificarAgroFauna`, tick de 200ms) y `RADIO_AGRO_DEFECTO=5` mayor que la distancia entre los dos spawns del propio fixture (~3.6), es fácil que el agro arrastre a "Jarl" a un combate contra un enemigo distinto ANTES de que le dé tiempo a mandar su propio `combate:iniciar` manual — que el servidor rechaza correctamente con `"ya estás en combate"` (`RoomExteriorBase.ts`, un jugador no puede abrir dos combates a la vez). La versión vieja del test ignoraba ese rechazo y localizaba un `combateId` cualquiera que contuviera el `objetivoId` esperado (con frecuencia el combate SOLO de "Centinela", del que "Jarl" nunca formó parte) y le mandaba `combate:comenzarYa` de todos modos — nadie con permiso real llegaba a registrar el roster de ESE combate (`registrarRosterArena`), así que `ArenaCombateRoom.onCreate` reventaba "Sin roster" al intentar consumirlo. **Arreglo real, en el test** (`client/test/mazmorraLimpiada.e2e.cjs::matarEnemigoReal`): antes de mandar `combate:iniciar`, comprobar si el propio jugador YA está en un combate propio (agro automático) y, si es así, seguir ESE — nunca asumir el `objetivoId` preferido; el objetivo real se resuelve leyendo el `bando` contrario dentro del combate ya confirmado, nunca a ciegas.

**Bug real nº2 — server, de verdad en `RoomExteriorBase.ts`, no solo del test: la auto-unión de `cerrarVentanaCombate` podía DOBLE-RESERVAR el mismo enemigo/fauna/npc en DOS `CombateSchema` pendientes a la vez.** Con dos jugadores cerca (el mismo escenario de arriba) es normal que el agro cree DOS combates "pendiente" casi simultáneos, uno por enemigo, cada uno con su propio jugador. Cuando el PRIMERO de esos combates cierra su ventana, su bucle de auto-unión (`for (const [id, e] of this.state.enemigos.entries())`, pensado para sumar refuerzos hostiles cercanos, docs §7bis/§7ter) solo comprobaba `combate.unidades.has(id)` (¿ya está en ESTE combate?) — nunca si `id` ya era parte de OTRO combate pendiente distinto. Así, el enemigo del SEGUNDO combate (el de "Jarl") podía colarse por cercanía en el roster del PRIMERO (el de "Centinela", quien nunca sigue a ninguna arena) — quedando reservado en DOS `CombateSchema` a la vez: uno que de verdad se resuelve en una arena, y otro que nadie cierra nunca (ni timeout de 60s alcanzado durante el test, ni ninguna acción de cliente), con una unidad fantasma. Confirmado empíricamente con logs temporales: el roster de un combate de agro llegó a registrarse con `["Jarl", "e_1", "e_0"]` — el enemigo "e_0" venía de un SEGUNDO combate pendiente (el de "Centinela") que jamás se cerró. **Arreglo real** (`RoomExteriorBase.ts::cerrarVentanaCombate`, los 3 bucles de auto-unión — enemigos/fauna/npcs): añadido `this.combatePorUnidad(id) || this.enOtraArena.has(id)` al guard de cada uno, mismo criterio simétrico que ya usaba `verificarAgroFauna` para no agroear dos veces a la misma entidad — un enemigo ya pendiente en OTRO combate, o ya peleando en otra arena, nunca se auto-une a un tercero.

**Límite real nº3 del propio test — el "Centinela" quedaba dragado como co-atacante fantasma sin ningún cliente que jugara sus turnos.** Con el bug nº2 ya arreglado, el co-op real (§9.1, comportamiento intencional: "Jarl" se une al combate que ya tenía "Centinela" contra el mismo enemigo) seguía dejando a "Centinela" como unidad `esJugador` sin ningún cliente que hiciera `joinOrCreate("arena", ...)` — el margen de gracia de `saltarTurnoSiJugadorAusente` (§11bis, 8s) sí evita el softlock total, pero con 3 combatientes en vez de 2 cada turno perdido de "Centinela" costaba ~8-10s reales, agotando el presupuesto fijo de 200 rondas del bucle de combate del test antes de que el enemigo muriera de verdad. **Arreglo real, en el test**: `seguirCentinelaAArenas()` — en cuanto "Centinela" recibe SU PROPIO `portal:ir` de combate, sigue a esa arena con su propia conexión (colyseus.js permite varias rooms abiertas a la vez en el mismo `Client`, sin dejar la mazmorra) y pasa turno cada vez que le toca — un aliado presente pero pasivo, nunca un turno huérfano esperando el margen de gracia. De paso, `rondas` (el presupuesto del bucle de combate del test) se redefinió para contar SOLO turnos reales del jugador que ataca, no los ciclos de espera del turno de otro — con 3 combatientes en vez de 2, contar también la espera diluía el presupuesto real de acciones a la mitad sin motivo.

**Límite real nº4 del propio test — movimiento voraz sin conciencia de obstáculos, se podía quedar pegado a una esquina para siempre.** Investigando el ÚLTIMO síntoma que quedaba (una ejecución con el enemigo en `40/40` de HP durante las 200 rondas enteras, `errorArena` siempre `"fuera de alcance"`) se confirmó con un diagnóstico de HP temporal que Jarl NUNCA se acercaba: el movimiento del test es un único paso diagonal voraz hacia el objetivo (`gx+dx, gy+dy`) sin ninguna noción de los obstáculos reales de la arena (`combate.obstaculos`, un mapa distinto por combate vía `elegirArena`) — en una rejilla táctica, un paso diagonal exige las dos casillas ortogonales adyacentes libres (mismo criterio que la mayoría de tácticos por turnos), así que una esquina bloqueada podía rechazar SIEMPRE el mismo movimiento diagonal sin que el test probara ninguna alternativa. **Arreglo real, en el test**: si el paso diagonal no mueve de verdad a Jarl (posición sin cambios tras el intento), probar los dos pasos ortogonales sueltos (solo horizontal, solo vertical) antes de rendirse ese turno.

Los 4 arreglos son honestos sobre dónde vive cada uno: nº1 y nº2 son bugs reales de `server/src/rooms/base/RoomExteriorBase.ts` (nº2 en particular podía afectar a CUALQUIER combate real con auto-unión bajo carga — fauna peligrosa §7bis, patrulla bandida §7ter, enemigo de mazmorra §11 — no solo a este test, aunque hacía falta la combinación "dos combates pendientes casi simultáneos cerca uno del otro" para disparar el doble-reservado, algo raro fuera de un escenario con varios jugadores agrupados); nº3 y nº4 son límites reales del propio harness de test (`client/test/mazmorraLimpiada.e2e.cjs`), no del servidor — un jugador real nunca "sigue pasivamente sin cliente" a una arena, y el cliente real (`client/src/game.ts`) nunca asume a ciegas un `combateId` sin haber recibido su propio `portal:ir`, así que ningún jugador real estaba expuesto a nº1/nº3/nº4 tal cual — pero nº2 SÍ es un bug de producción real, ahora cerrado.

Verificado: `client/test/mazmorraLimpiada.e2e.cjs` en verde en **35 ejecuciones consecutivas** repartidas en varias tandas tras el arreglo completo (12+12+15, cero fallo — antes de terminar el nº3/nº4 seguía fallando ~1 de cada 4-8 según qué límite del test tocara esa semilla), servidor 1236/1236 sin regresión, `tsc --noEmit` limpio en cliente y servidor. Los logs de diagnóstico temporales (`console.error` en `registroArenas.ts`, `RoomExteriorBase.ts`, `ArenaCombateRoom.ts`, y en `node_modules/@colyseus/core` — este último nunca comiteado, gitignored) se retiraron todos tras confirmar la causa raíz; el único rastro que queda en el código de producción son los 2 guards nuevos de `cerrarVentanaCombate` (nº2) con su comentario explicando el porqué.

Verificado: `server/test/lootProcedural.test.ts` +5 tests (catálogo temático con los 7 temas y sus itemIds reales; sin `temas` nunca cuela loot temático en 200 tiradas; tema desconocido no revienta; con tema real cae AL MENOS una vez y NO siempre en 300 tiradas — confirma que es probabilístico de verdad, ni 0% ni 100%; `temasDeEnemigo` real y con fallback vacío), `server/test/inventario.test.ts` (conteo exacto del catálogo 558→572, +14), `taller-vox/test_items.js` (conteo de armas clasificables 31→38, las 7 nuevas clasifican solas sin tocar el clasificador), servidor 1236/1236, `tsc --noEmit` limpio, `taller-vox/test_edificio.js`+`test_hitos_plaza.js`+`test_pj.js`+`test_muebles_proporcion.js` 50/50 sin regresión, y generación real de los 26 enemigos humanoides (`generarEnemigo`, 0 fallos, piezas de ropa/voxelesCabeza sensatas por archetipo) confirmando que ningún `prendaId` nuevo revienta el pipeline offline. **Sin verificación visual en cliente real esta pasada** (equipar una de las 14 piezas nuevas y mirarla en pantalla, o entrar a una mazmorra y ver a un enemigo con su ropa nueva puesta) — mismo gap ya aceptado varias veces este mismo día por presión de tiempo, documentado aquí en vez de darlo por bueno sin más.
